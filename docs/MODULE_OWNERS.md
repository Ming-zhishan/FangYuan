## 共同维护的文件如何处理

| 涉及的改动 | 需要协调的角色 | PR 至少说明什么 |
| --- | --- | --- |
| 数据表、来源记录、召回、更正与停用 | 数据责任人与实际调用方 | 数据兼容、隐私场景、原始与派生资料、相关回归；不直接操作生产库 |
| 发送回执、底层接口、模块加载和卸载 | 平台责任人与业务调用方 | 当前调用链、装载位置、发送前后状态和失败语义 |
| 模型配置、路由和用量治理 | 平台责任人与学习/复核调用方 | 前后台行为、已有授权、回退和用量证据 |
| 媒体选择与对话语境 | 媒体及对话责任人 | 选择依据、静默/回退、素材准入；不改变发送授权 |
| 共享配置结构及模板 | 平台责任人与受影响角色 | 配置键含义、默认值、兼容范围；模板不覆盖生产 |
| README、架构与进度 | 文档责任人与成果负责人 | 可定位提交、测试/验收范围及尚未确认的内容 |

主责任人未指定时，只在独立任务区准备补丁与说明，交由用户或其指定集成人员处理，不抢写共享工作区或生产文件。读取其他模块不产生修改授权。

## 每项任务的最小交接

1. 开始前记录任务、角色、基线提交、唯一工作树/分支、可写文件范围和只读输入。
2. 修改同一公共文件前核对他人的工作；需要扩大范围时说明接口变化并协调归属，不覆盖未提交文件。
3. 两套模块的差异尚未整合，说明实际修改哪一套、由谁装载、镜像是否需同步及保留哪些有意差异。
4. 执行相关离线检查，记录命令、结果、合成或真实环境的范围；不重复运行无变化的全项目测试。
5. 通过独立 PR 交付文件、验证、已知限制和下一接任入口。状态用代码、离线、集成、部署和真实效果分别描述。
6. 合并、部署和实际 QQ 验收分别处理；涉及生产、模型调用或真实发送的既有授权限制继续有效。

多人或多个 AI 即使共用 GitHub 账号，也应各用独立工作树与可追踪分支。同账号的自检不能冒称不同人的独立审查。平台权限和自动检查尚未建立的地方，明确记录限制，不能只写一条规则就宣称已有技术保护。
