# 离线自动检查与主分支保护

更新日期：2026-11-03。工作流见 [offline-checks.yml](../.github/workflows/offline-checks.yml)。它为 main 的 PR、main 推送及手动运行配置 Windows / Linux 两项检查，使用固定提交版本的官方 Actions、只读仓库权限，不保存检出凭据，不使用生产环境或模型密钥。

## 检查内容

- PR 从共同祖先到 PR 头提交审计完整变更；main 推送检查推送前后范围。手动运行检查最近一次提交。
- `tools/audit-range.mjs` 仅接受完整提交编号，在任务创建的临时无源码检出工作树中构建审计索引，复用暂存审计器；结束后清理自身临时工作树，不改变原工作区及索引。
- 在 Node 24 运行 `npm run test:repo`，另在 Python 3.12 运行试听反馈门禁。测试只使用合成数据；安装运行时及 Actions 需要网络，但不连接 QQ、模型或生产数据库。
- 继承于基线的旧文件不纳入本次差异扫描，不能把自动检查通过理解为历史隐私已清理。
- PR 使用普通 `pull_request` 事件，不使用拥有写权限的 `pull_request_target`。不提供仓库 Secrets，也不为测试安装真人媒体或模型。

## 主分支保护的建议值

自动运行检查与强制保护是两件事。工作流文件不能自行开启保护，必须在仓库管理设置另外配置，首次云端检查成功后再绑定下列状态名称：

| 设置 | 建议 |
| --- | --- |
| 目标分支 | main |
| 必经 PR | 开启 |
| 必须通过的检查 | `offline-ubuntu-latest`、`offline-windows-latest`，以真实运行返回的名称核对 |
| 合并前更新到最新主线 | 开启 |
| 强制推送、删除分支 | 禁止 |
| 管理员绕过 | 不允许日常绕过 |
| 独立批准人数 | 尚未登记独立审查者，先不要设置为无法满足的 1 人；成员到位后再启用 |

目前 GitHub 集成没有写入仓库管理设置的接口；授权设备离线时也无法核查其他已登录管理方式。不得因为账号的仓库元数据显示 admin，就宣称当前工具具有管理设置写权限。

工作流已提交、云端运行成功、保护规则已启用，应分别在 PR 和运行记录中确认。若上传工作流被平台拒绝，记录原始错误类别和缺少的权限，不通过其他接口规避权限限制。
